# 40 — `K_FR_T_ADAPT` / `FRA_TIMER` バグと A/C アイドルハンチング

コミュニティが言う「アイドリングバグ」の正体。
**アイドル制御（LFR/LLR/LLS）の較正バグではなく、Terra 改変バイナリの「プログラム 1 命令」のバグ**で、
充填レギュレータ適応（Füllungsregler-Adaption, FRA）を事実上停止させる。

症状は **「A/C ON でアイドルハンチング」「アイドルが理論空燃比に収束しない」**。

## 2. 機構

1. **M3(32300) ブートローダ**は Master 側で `K_FSP_CONCEPT` を **`0xE002` の 1 バイト**として読む
   （CSL レイアウトではそこは `K_FR_T_ADAPT` の上位バイト）。判定は `!= 0` のみ。
2. 素の CSL は `K_FR_T_ADAPT = 0x0096`（16bit, `X/100` sec = 1.50 s）→ 上位バイトが `0x00`
   → ブートローダが `K_FSP_CONCEPT == 0` と誤認 → **故障コードが読めない**。
3. **Terra の旧修正（2020）**: `0xE002 = 0x01`（センチネル）、`0xE003 = 0x96` とし、
   さらにプログラムを **1 バイト読み**に改変。
   ビッグエンディアン 68k では `(A1)` への `MOVE.B` は**ワードの上位バイト**に入るため
   `FRA_TIMER = 0x96 × 256 = 38400 tick × 10 ms = 384 s = 6.4 分`。**FRA がほぼ発動しない。**
4. **Community Patch v1**: 命令を **`MOVE.W 0x0008E002` に戻し**、値を `0x0100` に設定。
   上位バイト `0x01` でブートローダを満たしつつ、`256 tick × 10 ms = 2.56 s` の正しい時間。

### 裏付け（逆アセンブル）

`decomp/master/025572.txt:11`（`/* The below line differs from 1801 */` 付き）:

```c
FRA_TIMER = CONCAT11(K_FR_T_ADAPT, (undefined1)FRA_TIMER);
```

`CONCAT11(hi, lo)` = `(hi << 8) | lo`。読んだバイトが上位半分に入る。

`FRA_TIMER` が 16bit であることの確認:
`0x02562C: 53 51` = `SUBQ.W #1,(A1)`、`0x02559A: 4A 51` = `TST.W (A1)`。`A1 = 0x00FFE9F8`。

## 3. ★パーシャル BIN の設定（プログラム系統別・完全表）

**`0xE002`–`0xE003` の意味はプログラム側の命令によって変わる。** これが最重要点。

### (a) プログラム系統ごとの読み方

| プログラム | フル BIN `0x25630` の命令 | `FRA_TIMER` の作られ方 |
|---|---|---|
| 純正 CSL 0401 | `MOVE.W ($0008E002)` | `word@0xE002` |
| **Terra 改変** | `12 B9 00 08 E0 03` = `MOVE.B ($0008E003).L,(A1)` | **`byte@0xE003 × 256`**（下位は前回値の残り） |
| Community Patch v1 | `32 B9 00 08 E0 02` = `MOVE.W ($0008E002).L,(A1)` | `word@0xE002` |

### (b) パーシャル BIN の値 × プログラム → 実効値

| パーシャルの `0xE002-3` | 純正 CSL プログラム | **Terra プログラム** | **CP v1 プログラム** | M3(32300) BL の DTC 読取 |
|---|---|---|---|---|
| `00 96`（素の CSL 出荷値） | 150 tick = **1.50 s** ✅ | 0x96×256 = **384 s** ❌ | 150 = **1.50 s** ✅ | ❌ 上位バイトが 0 |
| `01 96`（**Terra 出荷値**） | 406 = **4.06 s** △ | 0x96×256 = **384 s** ❌ | 406 = **4.06 s** △ | ✅ |
| `01 00`（**CP v1 出荷値**） | 256 = **2.56 s** ✅ | 0x00×256 = **0** ❌ **危険** | 256 = **2.56 s** ✅ | ✅ |
| `01 01`（Terra 用・**導出／未検証**） | 257 = 2.57 s ✅ | 0x01×256 = **2.56 s** ✅ | 257 = 2.57 s ✅ | ✅ |

### 読みどころ

- **Terra プログラムの DME に CP v1 の `01 00` を書き込んではならない。**
  上位バイトに `0x00` が入り FRA_TIMER が 0 近傍になって適応が 10 ms ごとに暴走する。
  「Community Patch の値をパーシャルにコピーする」は Terra 系では**誤り**。
- Terra プログラムのままパーシャルだけで直すなら **`01 01`** が理屈上の正解。
  ただし**これは本解析による導出でありコミュニティ未公表**。採用するならベンチ／実車確認が必要。
- **プログラム領域（`0x25630`）は 64 KB パーシャル BIN に含まれない**ため、
  パーシャルだけを見てプログラム系統を断定することはできない。
  副次マーカーによる推定は `50-binary-lineage.md` §3。
- **推奨は「フル BIN を Community Patch v1 に更新すること」。** パーシャル側の小細工は代替手段。

> このツールは `0xE002` に対して**読み書きを一切しない**。プログラム系統を確証できない以上、
> 誤判定時の被害（適応の暴走）が大きすぎるため。

## 4. なぜ「アイドル」と「λ」に効くのか

Funktionsrahmen `2.03 Adaption Füllungsregler`（原文和訳）:

> 「充填レギュレータ適応の役割は、スロットルバルブの組付け・製造ばらつき
> （車両ごとに異なる**漏れ空気 Leckluft**）に起因する、算出された目標充填と
> 実測充填との**定常的な差**を補償することである。この偏差を FR 適応が検出し、
> 算出 `ml_soll` の補正によって解消する。」

```
  A/C コンプレッサ ON（ステップ負荷）
      ↓
  FR（充填レギュレータ, PI）が 目標充填 と 実充填 の偏差を埋めにいく
      ↓
  FR の I 分に残る定常オフセットを消すのが FRA（適応）
      ↓ ★ここが 1.5 s → 384 s に化けている
  オフセットが残ったまま ml_soll 系に誤差
      ↓
  RF / ML がずれる → 噴射時間 TI がずれる
      ↓
  λ が約 5% リーンに張り付き、閉ループでも収束しない
      ↓
  アイドル空気量・トルクの読み違いと相まって A/C ON 時にハンチング
```

漏れ空気の影響が最大になるのは**アイドル〜微開度**。
だからステップ負荷である A/C コンプレッサの入切で最も顕在化する。

近傍パラメータ（いずれも FÜLLUNGSREGLER 群、Master）:
`K_FR_DMLADAPT_MAX` `0xE000` / **`K_FR_T_ADAPT` `0xE002`** / `K_FR_MLADAPT_MAX` `0xE004` /
`K_FR_MLADAPT_MIN` `0xE006`

## 5. もう一つの A/C アイドルハンチング（純正 CSL でも起きる方）

karter16 が「別問題」と明言した、**純正 CSL ブートローダでも起きる古典的な A/C アイドルハンチング**。
**フォーラムに公開された解決策は存在しない**（thread 230915 全 9 ページ。Kessel が非公開の DME 設定
1 つで約 75 % 改善、HTE が「ほぼ起きない所まで追い込んだ」が、いずれも値は非公開）。

ただし**バイナリ側の機構は特定できている**。4 つの要因が重なる。

### 要因 1：A/C でアイドル目標回転数が上がらない

- `SCHALTER_CAN & 4`（A/C 要求）で目標を `K_LFR_NSOLL_AC` へ引き上げる
- **`K_LFR_NSOLL_AC` @ `0x9A4A` = `0x0366` = 870 rpm**
- しかし `KL_LFR_NSOLL_GRUND`（`0x9A64` / `0x9A6C`）の暖機後の値も **50 °C・80 °C ともに 870 rpm**
  （−30 °C:1050 / 20 °C:920 / 50 °C:870 / 80 °C:870）
- → **暖機後はどの水温でも引き上げ幅がゼロ**。制御器は同じ設定回転数のままコンプレッサの
  ステップ負荷を丸ごと吸収させられる
- （Andratch がフォーラムで「OEM は 870 rpm」と書いた値と一致する。彼の車では 950 rpm に
  変えられていた＝チューナーはここを触っていた可能性が高い）

### 要因 2：コンプレッサ負荷フィードフォワードの時定数が 78 倍非対称

`md_klima_filter` が IHKA から CAN で来るコンプレッサトルク要求 `CAN_KKOS_LM` を PT1 追従する
（`decomp/master/017748.txt`）。

| 向き | 定数 | 値 | 時定数（20 ms タスク） |
|---|---|---|---|
| 入り | `K_MD_MIN_KKOS_FILTER` | 1/256 | **約 5.1 秒** |
| 抜け | `K_MD_MIN_KKOS_AUS_FILTER` | 78/256 | **約 0.066 秒** |
| 係合時シード | `K_MD_MIN_KKOS_START` | 20/32 = 0.625 | 要求の 62.5 % から開始 |

→ **負荷はゆっくり乗り、急に抜ける。** コンプレッサがサイクルするたびに非対称な外乱になる。

### 要因 3：オーバーシュート側の権限が無い

- P 項 `KL_LFR_DQP_POS`（`0x9ABE` / データ `0x9ADE`）は **`dn > 0`（回転が低い側）でしか評価されない**
- 点火による速い修正 `KL_LFR_TZ_NEG`（`0x9CE6` 系）は **全ゼロ**
- → **回転が上がりすぎた時の戻しは、遅い I 積分 `KF_LFR_DQI`（`0x9B84`）だけ**。
  非対称 FF（要因 2）で吹け上がった分を遅い積分でしか戻せない＝振動しやすい

### 要因 4：適応がコンプレッサ入切のたびに積分器を切り替える

- `lfra_adapt`（`decomp/master/025b52.txt`）が `LFRA_MD_INTEGRATOR`（OFF 用）と
  `LFRA_KO_MD_INTEGRATOR`（ON 用）を `KKOS_ST` bit0 で**切り替える**
- 1 フェーズの移動量は `K_LFR_DMDADAPT_MAX` = **1.0 Nm** に制限、
  ロック時間 `K_LFR_T_ADAPT` = 3 s、時定数 `K_LFR_TAU_ADAPT` = 15.06 s
- 適応した分は `LFR_MDI`（I 項）から直接差し引かれる
- → **切替直後は必ず適応が追いついていない状態**になり、そこへ要因 2 の外乱が来る
- 加えて **LLSync が A/C 作動中もブロックされない**（`K_LL_AKTIV_CONTROL` @ `0x1013` = `0xBF`
  ＝ bit6「コンプレッサ作動中はブロック」が**クリアされている**）ので、
  外乱の最中に気筒別 `ti` 学習が走る

## 6. 併せて疑うべき：ICV 故障によるアイドル開ループ

`30-idle-control.md` §7 条件 1。
`LLS_ST` bit7（アイドル調整弁故障ラッチ）＋ アイドル状態 → **アイドルでだけ λ 開ループ**。
スロットルを開けた瞬間に閉ループ復帰するので、
「アイドルだけ空燃比がおかしい」という症状はまずここを確認する価値がある。
`LLS_ST` は `lls_diag`（`decomp/master/02603a.txt`）が `|= 0x80` でラッチする。
