## 1. 結論 —— 書き込みセルが減った原因は、統計ではありません

Session #923（6,739 点、負荷帯にデータのあるセル 64 個）を、現行コードと、
**ハードゲートだけを外したコード**の両方に通して比較しました。

```
                                 セル数    共有セルでの値の最大差
  両方が書くセル                    10        0.00e+0   ← 完全に同一
  ハードゲートを外したときだけ書く   21
  ハードゲートがあるときだけ書く      0
```

**ハードゲートは値を一切変えていません。答えを 21 個消しているだけです。**

> この比較の「ハードゲートなし」は、`shared-evidence` / `thin-independent` / サンプル下限だけを
> 外し、**収縮 λ は残した**ものです。だから値が完全に一致しました。実装した `DIRECT` は λ も
> AUTHORITY に置き換えるので、値は**わずかに大きく**なります（λ は 1 に漸近するだけで 1 には
> ならないため。証拠の厚いセルでテーブル 1 目盛より小さい差）。

「厳しくして精度を上げた」のであれば、残った 10 セルの値は変わるはずです。変わっていません。
つまりゲートは品質を上げておらず、**証拠のあるセルを捨てているだけ**でした。あなたの違和感は正しいです。

### 何が消えたか

高負荷側の書き込み量（%）。`.` はデータはあるが書かないセル。

```
現行（10 セル）                        ハードゲートなし（31 セル）
 aq_rel_rf  1800   2100   2200   2400    1800    2100    2200    2400
  100 %      .      .      .      .     -17.1% -16.8% -14.6% -13.2%
   85 %      .   -16.6% -14.9% -11.9%   -15.0% -16.6% -14.9% -11.9%
   65 %   -11.1% -12.6%    .   -10.2%   -11.1% -12.6% -15.0% -10.2%
   45 %      .      .      -      -     -11.3% -11.1%    -      -
```

右は**なめらかな面**です。開度が上がるほど補正が深く、回転が上がるほど浅い。
充填モデルの誤差はまさにこの形をしています。

左は穴だらけで、しかも**穴の開き方が有害**です。2200 rpm の列を縦に読んでください:

| 開度 | 要求 | 現行の結果 |
|---|---|---|
| 100 % | −15 % | **書かない**（純正のまま） |
| 85 % | −15 % | **−14.9 % 書く** |
| 65 % | −15 % | **書かない**（純正のまま） |

三つとも同じ −15 % を要求しているのに、真ん中だけ書きます。焼いたあと、
**65 % → 85 % → 100 % と開けていくと、負荷信号が 15 % 落ちて 15 % 戻ります。**
純正テーブルには無かった段差を、こちらで作っていることになります。

**全部書くか、全部書かないか、どちらでも今よりましです。** これは「保守的すぎる」ではなく、
**一貫していない**という別種の欠陥です。

### どのゲートが落としているか

```
  ゲート               落としたセル   要求補正の中央値   最大
  thin-count               22           6.93 %       17.13 %
  shared-evidence          18           6.55 %       16.78 %
  not-significant          12           0.61 %        4.60 %
  thin-independent          2           7.04 %        7.04 %
  （書き込み）              10          11.73 %       16.60 %
```

読み方が全てです。

- **`not-significant`（t 検定）が落とした 12 セルは、中央値 0.61 % しか要求していません。**
  これは正しい動作です。ノイズと区別できない小さな補正を書かない、という仕事をきちんとしています。
  最大でも 4.6 %。**統計は無実です。**
- **`shared-evidence` が落とした 18 セルは中央値 6.55 %、最大 16.78 %。**
  100 %/2100 の −16.8 %、100 %/2200 の −15.3 %、85 %/1800 の −15.1 % —— 全部ここです。
- `thin-count`（サンプル 10 未満）が 22 セル、中央値 6.93 %。

**消しているのは `shared-evidence` と `thin-count`。どちらも統計的検定ではなく、私が置いた固定のバーです。**

## 2. 用語 —— レビューに要る 4 つだけ

### 重み (weight)

ログの 1 点は、必ず 4 つのセルの間に落ちます。ぴったりセルの真上に乗ることはまずない。
そこで**距離に応じて 4 セルに分配**します。合計は 1.0。

```
   65 %  ┌──────────┬──────────┐
         │  0.06    │   0.14   │
         │          │          │
         │        × ←ログの1点 │
   45 %  ├──────────┼──────────┤
         │  0.24    │   0.56   │
         └──────────┴──────────┘
        2100 rpm            2400 rpm
```

真ん中に落ちれば 4 セルに 0.25 ずつ。角に落ちれば 1 つのセットに 1.0 近く。
だから**「サンプル 10 個」でも重みは 2.5 かもしれないし 10 かもしれません。**

### 自己シェア (self-share) ← 今回の主犯

そのセルが集めた重みのうち、**自分の分がどれだけか**。`Σw² / Σw`。

- 全部が自分の真上に落ちていれば 1.0
- 全部が隣との境目なら 0.25

現行コードは **0.30 未満のセルを拒否**します。理屈は「証拠の大半が隣のセルの話だから」。

**この理屈が成り立つのは、隣が違うことを言っているときだけです。**
上の表を見てください。拒否された 100 %/2100 の隣（85 %/2100）は −16.6 % で書かれています。
100 %/2100 自身の要求も −16.8 %。**隣は同じことを言っている。** 借りた証拠は正しい証拠でした。

しかも拒否したときの代替は「純正値のまま」です。**純正値は 15 % 間違っていると、この測定自身が
言っている値です。** 「隣から借りた、たぶん正しい値」と「確実に 15 % 間違っている値」を比べて、
後者を選んでいることになります。

### 自己相関 (ρ) —— ここは私が正しいと思っています

`la_f_regler`（λ 補正）は**2 点制御**です。上下に振り続けるスイッチで、
1〜2 Hz で振動しています。ログは 4〜5 Hz。

```
  真の値 ────────────────────────
  λ     ╱╲    ╱╲    ╱╲    ╱╲
       ╱  ╲  ╱  ╲  ╱  ╲  ╱  ╲
  ログ  ●●●●  ●●●●  ●●●●  ●●●●     ← 1回の振れを3〜4点で読んでいる
```

**連続する 4 点は、独立した 4 つの測定ではありません。1 回の振れを 4 回読んだだけです。**
サンプル 100 個は情報 100 個ぶんではない。実測 ρ ≈ 0.85（低開度 0.756 / 高負荷 0.923）。

これを無視すると「精度が高い」と誤認して、ノイズを書き込みます。
**この補正自体は正しく、EFI Analytics 系のツールが一般に見ていない点です。** 残すべきです。

### 収縮 λ ← ここが設計の要

セルを「書く／書かない」の二択にせず、**証拠の量に応じて動かす量を決める**仕組み。

```
  λ = 1 − (t95 / t)²            実際に動く量 = 要求 × λ
```

証拠がぎりぎりなら λ ≈ 0 でほとんど動かない。証拠が厚ければ λ ≈ 1 で要求どおり動く。
**連続的で、崖がありません。**

実測（現行の 10 セル）:

| セル | 要求 | 実際に書いた量 | λ |
|---|---|---|---|
| 85 %/2100 | −16.60 % | −16.57 % | 100 % |
| 65 %/1800 | −11.73 % | −11.12 % | 95 % |
| 7.5 %/2700 | −1.99 % | −1.31 % | 66 % |
| 5 %/2700 | −0.81 % | −0.22 % | 27 % |

**この仕組みがあるなら、ハードゲートは要りません。** 証拠の薄いセルは λ が小さくなって
勝手にほとんど動かないからです。証拠が薄いセルを λ で 3 % だけ動かすのと、
拒否して 0 % にするのと、後者が優れている理由はありません。

> **重要**: 現行コードは λ と ハードゲートの**両方**を持っています。
> λ が来る前にハードゲートがあり、λ を足したときに古い方を外さなかった。
> 同じ仕事を、粗いやり方と細かいやり方で二重にやっています。

## 3. EFI Analytics との違い —— どちらが正しいか

EFI Analytics 系のツール（VE Analyze など）の設計思想:

> **1 回で当てにいかない。** 小さめの補正を当てて、走って、また当てる。誤差は繰り返しで消える。

これは制御として正しい考え方です。**低ゲインの積分器**であり、
毎回少しずつ真値に近づく（縮小写像）。1 回ごとの精度は要らない。だから
「重み 0.1 以上なら書く」で構わない。**ループが精度を作る**からです。

私が作ったのは違う質問でした:

> **この 1 回で、このセルの補正を 95 % の確信をもって主張できるか。**

これは論文を書くときの基準です。**1 回で決着させる前提の質問**であり、
繰り返し走って直していく作業には合っていません。

**そして 95 % という水準に工学的な根拠はありません。** 判断すべきは損得です:

- 純正のまま放置するコスト = **15 % ずれた負荷信号**（点火時期・トルク要求・全部これで動く）
- 余計に書いてしまうコスト = **2 % ずれた 1 セル。次回のログで直る**

**まったく釣り合っていません。** 非対称なのだから、バーは 95 % よりずっと低い側に置くべきです。

### 整理すると

| | EFI Analytics の考え方 | 現行実装 | あるべき姿（私見） |
|---|---|---|---|
| ループ | ○ 繰り返し前提 | ✗ 1 回で決めようとする | **EFI Analytics 側** |
| ゲイン | ✗ 固定（authority %） | ○ 証拠に応じた λ | **現行側** |
| 自己相関 | ✗ 見ていない | ○ 見ている | **現行側** |
| 書く／書かない | ○ ほぼ全部書く | ✗ ハードゲートで削る | **EFI Analytics 側** |

**EFI Analytics はループが正しく、現行実装はゲインが正しい。現行実装はゲインを手に入れたときに、
ループを壊しました。**

## 4. 判断が要るところ

以下は私が決めるべきことではないので、選択肢として置きます。

### ① ハードゲートを外すか

外す対象:

| ゲート | 現在 | 提案 | 理由 |
|---|---|---|---|
| `shared-evidence` | selfShare ≥ 0.30 | **削除** | 隣が一致していれば借りた証拠は正しい。λ が既に効いている |
| `thin-count` | rawCount ≥ 10 | **1〜3 に下げる** | 統計量を計算できる最低限だけあればよい |
| `thin-independent` | nIndep ≥ 3 | **削除** | t 検定が同じ判定を連続的に行っている |
| `not-significant` | t > t95 | **残す** | ただし 95 % → 80 % 程度を検討（上の損得の非対称性） |
| `scatter` | sd ≤ 0.08 | **残す** | これは精度の話ではなく「2 つの状態が混ざっていないか」の妥当性検査。別物 |
| `out-of-band` / `no-evidence` | — | **残す** | 所有権とデータ有無。ゲートではない |

**未検証の懸念**: ハードゲートなしの結果で、65 %/2900 が +6.2 %、45 %/2700 が +3.0 % と、
周囲が全部マイナスの中で符号が反転しています。本物の構造か、ノイズかは分かりません。
外すなら、**「隣と符号が違うセル」を見る仕組み**（空間的な平滑化／近傍との整合チェック）が
`shared-evidence` の正しい後継になるはずです。単に外すだけだと、この 2 セルは通ります。

### ② `not-significant` の水準

95 %（両側）は科学出版の慣習であって、工学の判断基準ではありません。
損失の非対称性からは 80 % 前後が妥当に見えますが、**これは数字を選ぶ問題なので、
根拠を作ってから動かすべき**です。今は提案に留めます。

### ③ 実車で決着させる

どちらの設計が正しいかは、**焼いて再ログを取れば直接分かります**。
書いたセルのトリムが 1.000 に寄れば正しい。寄らなければ間違い。
31 セル版と 10 セル版のどちらを先に試すかは、あなたの判断です。

## 7. 実装（2026-08-28）

軸を `DIRECT` に移しました。**現在の実装を消してはいません** —— 統計処理は選べる方式として全部残っています。

### 7.1 VE METHOD —— 二択の軸

RAW FILTER の **VE METHOD** 行。既定は **DIRECT**。

| | DIRECT（既定） | STATISTICAL |
|---|---|---|
| 問い | 今まで測った全部から、次のマップはどれか | この 1 回でこのセルを 95 % で主張できるか |
| 走るゲート | 帯域・データ有無・サンプル数（既定 3）のみ | + 自己シェア・独立性・散らばり・有意性 |
| 動かす量 | AUTHORITY（既定 100 %） | 収縮 λ = 1 − (t95/t)² |
| 使いどき | ふだん全部 | 収束したあとの最終確認 |

ゲートは**構造的**と**統計的**の 2 段に分かれました。構造的なもの —— `out-of-band`（低開度は
LOW LOAD の担当）、`no-evidence`（データが無い）、`thin-count` —— は**どちらの方式でも走ります**。
これらは統計ではなく「計算するものがあるか」の判定だからです。

`enableVeCellGate` トグルは UI から外しました。**あれは 6 つのゲートのうち 2 つしか動かしておらず**、
「ゲートを切った」と表示しながら自己シェア・独立性・有意性は拒否を続けていました。METHOD が正直な軸です。
保存済みセッションの値は尊重され、パネルに退役設定として表示されます（解除ボタン付き）。

### 7.1.1 名前について —— なぜ `DIRECT` で、他社名ではないのか

この方式の考え方は EFI Analytics 系のツール（VE Analyze など）から採りましたが、
**モード名に他社の製品名は使いません。**

- 提携も承認も無いのに、あるように読めます
- **あの製品のアルゴリズムではありません。** 考え方が同じなだけで、実装は独自です
  （自己相関の扱いなど、あちらが見ていない部分もあります）

`DIRECT` は**動作そのもの**の名前です —— 測った値をそのまま書く。

ただし**由来は消していません。** `minCellWeight` の既定 0.1 が
EFIAnalytics の 10 Hz Testo ログ用の値だったという記録は
[calculator.ts](../../src/lib/ve-calculator/calculator.ts) と `verify:coverage` に残っています。
上の §3 も、他社ツールの設計思想の分析としてそのまま残しています。**帰属は帰属、ラベルはラベル**です。

なお `DIRECT` という語はループのことを何も言わないので、
**パネルの説明文の 2 行目が「1 回で当てにいきません」から始まる**ようにしてあります。
名前が根拠を語らないぶん、コピーが語ります。

### 7.2 AUTHORITY

測った要求のうち何 % を今回書くか。既定 100 %。

**下げる必要はありません。** 要求は書き込み前に 2 回抑えられています —— そのセル自身のサンプルが
出した範囲（アンチラチェット。焼いて再ログを繰り返したときにセルが際限なく歩くのを止める仕掛け）と、
`CORRECTION_MIN/MAX`。下げても安全にはならず、収束が遅くなるだけです。ログが荒れていて
1 回ぶん信用しきれないときだけ 50〜70 %。

0〜1 にクランプしてあるので、保存された壊れた値が補正を反転・増幅することはありません。

### 7.3 実測（Session #923、同じログ・同じベース）

```
                     書き込みセル   バイト
  STATISTICAL             10        11
  DIRECT（既定）          58        64
```

高負荷側が面としてつながりました:

```
 aq_rel_rf    1800     2100     2200     2400
  100 %     -17.1%   -16.8%   -15.3%   -13.2%
   85 %     -15.1%   -16.6%   -15.1%   -12.0%
   65 %     -11.7%   -13.0%   -15.0%   -10.7%
   45 %     -11.5%   -11.6%      -        -
```

§1 で問題にした「2200 rpm の 85 % だけが −14.9 %、上下は純正のまま」という段差は消えています。

### 7.4 SHAPE は収束を要求します

SHAPE は**面を制約集合に射影する**処理です（単調・ゲイン上限）。収束したマップに掛ければ
較正の欠陥が取れますが、**1 回の走行の出力に掛けると、その走行のノイズを滑らかで単調にします**。
均された誤差は元の凸凹より見つけにくい —— 意図してそうしたように見えるからです。

なので APPLY は**マップが動き止まるまで拒否**します。

判定は保存履歴ではなく、**今の導出そのもの**から取ります。連鎖の規則
（次のセッションの BASE ＝ 前回焼いたバイナリ）を守っていれば:

```
base(n) = tune(n-1)        ← 連鎖の規則
demand(n) ≈ 1              ← つまり前回のマップがこの走行を既に満たしている
```

要求がどこも 1.000 付近の走行は、**直すものが残っていない走行**です。それが収束です。
既定の帯は **±2 %**、判定に使うのはサンプル 3 個以上のセルのみ。

**測っていないマップは「収束」ではありません。** どちらも「動こうとしているセルが無い」状態ですが、
片方は終わっていて、もう片方はまだ何も分かっていない。`evaluated === 0` のとき `converged` は
false を返します —— これを取り違えると、**誰も走っていないベースの上で SHAPE が解除されます**。
`verify:convergence` がこの 1 点を固定しています。

REVERT は塞ぎません。既にマップに乗っている修正を戻すのは、危険な方向ではないからです。

### 7.5 まだやっていないこと

- **符号が隣と反転するセルの検査。** §4 で挙げた `shared-evidence` の正しい後継 ——
  「隣と整合しているか」を見る空間的な検査 —— は**実装していません**。`DIRECT` では
  65 %/2900 の +6.2 % のようなセルがそのまま通ります。収束の過程で消えるはずでしたが、
  **§8 で確かめたところ消えていません。**
- **`not-significant` の水準。** 95 % のままです。損得の非対称性からは 80 % 前後が
  妥当に見えますが、根拠を作ってから動かすべきなので触っていません。
  STATISTICAL 方式でのみ効きます。
- **LOW LOAD 側の自己相関。** `MAX_STD_ERR` は素朴な標準誤差に対して掛かったままです。
- ~~**実車で確かめていません。**~~ → **§8（2026-08-29）。** 同じベースの上で録った 2 本で
  確かめました。結果は下に書きます。

### 7.6 保存済みセッションへの影響

## 8. 実車での検証（2026-08-29）—— 同じベースの 2 本

§7.5 の最後の項目に、初めて答えが出ました。

### 8.1 なぜ「同じベースの 2 本」でなければならないのか

連鎖の規則（次のセッションの BASE ＝ 前回焼いたバイナリ）を守っていると、連続する走行は
**違うバイトに対して**測られます。動かしたセルは 2 回目に違う値を出す**べき**なので、要求どうしを
比べても、エンジンの性質と前回の書き込みが分離できません。

**兄弟** —— ひとつのフラッシュの子で、その間に焼いていない 2 本 —— なら同一バイトに対する測定なので、
同じセルの要求は**同じ量を 2 回測ったもの**になります。

| | Session #925 | Session #926 |
|---|---|---|
| 記録 | 8/28 19:27、13,560 点、56.7 分 | 8/29 08:03、10,795 点、43.1 分 |
| ベース | `014099d7…` | **同一** `014099d7…`（どちらも #924 のフラッシュの子） |
| トリム中立性 | 全点 `laa_f` = 1.000 | 全点 `laa_f` = 1.000 |
| DIRECT が書くセル | 14 | 46 |

### 8.2 DIRECT の前提は、2 本目に答えられていません

`calculator.ts` の `VeMethod` はこう書いています ——
「**この 1 回で決めなくてよい。次の走行が答える**」。答えていませんでした。

```
  両方に証拠のあるセル   14
  要求 #925 %   sd 1.92   p05 −2.69  p50 +0.92  p95 +2.99
  要求 #926 %   sd 1.53   p05 −1.84  p50 +0.83  p95 +1.64
  差 (B−A) %    sd 2.41   p05 −3.98  p50 +0.02  p95 +2.18

  符号の不一致   7 / 14
  相関 r = 0.038   95 % 区間 −0.50 .. 0.56 (n = 14)   B を A に回帰した傾き 0.030
  再現する成分  sd 0.33 %      走行ごとのノイズ  sd 1.89 % / 1.49 %
```

**2 本の差の広がりが、書いている補正そのものの広がりより大きい。**
`cov(A, B)` は再現する成分の分散そのもの（2 本のノイズは独立なので）で、それが sd 0.33 %。
n = 14 なので区間は広く、「無相関だと証明した」とは言えません。言えるのは **1.0 の近くではない**ことです。

同じ問いを、一番使う形で聞いたもの —— **焼いたら次の走行の誤差は小さくなるか**:

```
  #925 の補正を #926 の証拠に当てる   平均 |誤差| 1.33 % → 1.73 %   悪化（改善 4/12）
  #926 の補正を #925 の証拠に当てる   平均 |誤差| 1.63 % → 1.50 %   改善（改善 6/13）
```

差し引きゼロです。同じログを `STATISTICAL` に通すと #925 は 14 → **1** セル、#926 は 46 → **7** セル
（落ちる理由: `thin-count` 16 / `shared-evidence` 11 / `not-significant` 11 / `thin-independent` 1）。

**読み: 1 本の走行から取り出せる VE 信号は、DIRECT が書いている量より小さい。**
§1 の結論（ハードゲートは品質を上げずに答えを消していた）は Session #923 で正しかったのですが、
**逆側の限界がここにあります。** ゲートを全部戻すと 46 → 7 で使い物になりません。
`thin-independent` と `thin-count`（#926 では 3〜6 サンプルの 16 セル）だけを構造ゲートに戻すのが、
測定が支持している最小の変更です。**まだ実装していません。**

### 8.3 この比較で言えないこと

- **14 セルは少なく、帯が偏っています。** 両方が濃く踏んだ 5〜10 % 開度・2100〜3100 rpm に集中していて、
  高負荷側は #925 がほとんど踏んでいないので入っていません。§7.3 の −10〜−17 % の面は
  この検定を受けていません。
- **#926 は「気圧を 1 本の中で分離できた最初の走行」でもあります。** `corr(ln P, 時刻)` が
  #925 の **−0.927**（気圧と時計が同じ回帰子＝同定不能）に対して **−0.185**。
  上って下りたからです。`d ln(補正)/d ln(P)` は時間を入れて **−0.076**（入れないと −0.135 ± 0.048）で、
  `RF_PT_KORR` の割り戻しは概ね効いています。`analyze:pressure-pair` が 2 本を要求するのは
  **1 本では分離できない走行しか無かったから**で、それはもう常に真ではありません。

**再現**:

```
npm run analyze:same-base-pair -- <session-dir-A> <session-dir-B>
npm run analyze:session        -- <session-dir>
```

`analyze:same-base-pair` は 2 つのベースが一致しないと**走らずに落ちます** —— §8.1 の条件は
読み手が覚えておく前提ではなく、道具側の門です。
