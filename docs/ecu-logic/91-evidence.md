# 91 — 根拠の等級と、条件についての一つの規則

このディレクトリの文は「DME が何をしているか」を述べる。
その一文一文が**何を根拠にしているか**を、読み手が引用を見ただけで判定できるようにするのがこの文書。

`90-sources.md` が「資料がどこにあるか」の対応表であるのに対し、
ここは「どの資料が、どの主張を支えられるか」を決める。

---

## 1. 規則は一つだけ

> **条件・分岐についての主張は `[C]` を引く。**
> **`[G]` は「その関数が何に触れるか」には引けるが、「その条件が存在するか」には引けない。**

他はすべて推奨であって、これだけが規則である。理由は §3。

---

## 2. 等級

### 一次資料 — バイナリそのもの

| 等級 | 何か | 引き方 |
|---|---|---|
| `[B]` | `Full 211323000401PD31_TERRA.bin` から直接読んだバイト | `[B 0x9554 = 0x0140]` |
| `[C]` | Ghidra の逆コンパイル出力。`app/public/data/decomp/<bank>/<addr>.txt` | `[C master/021a70]` |
| `[X]` | XDF のアドレス・型・スケール・軸定義 | `[X KF_RF_KORR_DRREL]` |

`[B]` は値、`[C]` は手続き、`[X]` はその値をどう読むか。三つは互いを代替しない。
**スケールを `[C]` から主張してはならない**（逆コンパイラは生の整数しか見ていない）。
**手続きを `[X]` から主張してはならない**（XDF は表の形しか知らない）。

### 二次資料 — 一次資料の読み

| 等級 | 何か | 引き方 |
|---|---|---|
| `[G]` | `graph.json` / このアプリの解析結果。文・エッジ・境界 | `[G rf_korr stmts]` |
| `[D]` | このリポジトリの推論。まだ一次資料に当たっていないもの | `[D]` |

`[G]` は `[C]` を機械が読んだ結果である。**読みは、整った形のまま節を落としうる。**
だから `[G]` は `[C]` の代わりにならない。

### 外部資料

| 等級 | 何か | 引き方 |
|---|---|---|
| `[F]` | BMW/Bosch の Funktionsrahmen。節番号まで書く | `[F 4.01 pp.7-9]` |
| `[K]` | コミュニティ由来（karter16、掲示板、他車種の A2L） | `[K karter16 XDF v3.6]` |

`[F]` は**設計意図**の一次資料だが、**この 0401 の実装**の一次資料ではない。
7.0 の制御器が 0401 に存在しない例がすでにある（→ `90-sources.md` §2）。
Funktionsrahmen が言っていることと、このバイナリがしていることは、別に確かめる。

## 3. なぜ条件だけ特別扱いなのか

`[G]` は `[C]` を構文解析して作る。解析は行を読み、文と条件に組み直す。
**この組み直しは、失敗しても整った出力を出す。**

2026-09-04 の実測がその形を示している。逆コンパイラは桁で折り返すので、
`if` の条件が2行に渡ることがある:

```c
if ((((N != 0) && ((DAT_00ff8022 != 126 || (DAT_00ff8023 != -127)))) &&
    ((DAT_00ff8022 != 60 || (DAT_00ff8023 != -61)))) && ...) {
```

解析器は1行を1文として扱っていたため、この `if` に一致しなかった。
一致しなかった `if` は消え、**その中身は条件を持たない文として記録された**。

| | 件数 |
|---|---:|
| 折り返しで一致しなかった `if` | 1,158（465 関数） |
| その結果、無条件として記録されていた文 | **986** |

986 件は「情報が足りない」のではない。**「ECU はこれを無条件に行う」という、偽の主張**である。
そして出力は最後まで整っていた。欠けた節を示すものは何も無かった。

解析器は直した。規則が残るのは、これが**構造的な失敗様式**だからである。
`[G]` は読みであり、読みは黙って節を落としうる。条件は落ちても文の形が残る。
値やエッジが落ちれば数が合わなくなるが、**条件が落ちても数は合う**。

だから条件だけは、読みではなく原文を引く。

## 4. 引用の書き方

引用は行末に置く。複数可。

```markdown
`rf_korr` は `rf_korr_rf_min < rf_soll` かつ `k_rf_korr_v_min < V` の
両方が成立するときにのみ `rf_korr_drrel` を取り込む。[C master/021a70]

`KF_RF_KORR_DRREL` は 16×16、X 軸 rpm・Y 軸 TABG。[X KF_RF_KORR_DRREL]

充填レギュレータの適応は漏れ空気の補償が目的。[F 2.03]

この係数を 1.06 にしている実例がある。[K 掲示板]

アイドル時にこの経路が効いていると思われるが未確認。[D]
```

`[C]` の中身は `<bank>/<6桁hex>`、つまり `decomp/` 以下のファイル名そのもの。
`verify:cal-docs` はこれを実在するファイルとノードに突き合わせる。

---

## 5. 機械が見るもの、見ないもの

`npm run verify:cal-docs` が確かめるのは三つだけ。

1. `[C bank/addr]` の指す本文が実在し、その番地に関数ノードがあること
2. 本文中の `master 0xNNNN` / `slave 0xNNNN` が、成果物のノードか、関数の本体内であること
3. 引用されている ECU シンボルが成果物に存在すること

**確かめないもの**: その文が正しいかどうか。等級が適切かどうか。
機械に分かるのは「引用先が実在するか」だけで、
「その引用がその主張を支えるか」は人間が決める。

だからこの検査が通ることは、文書が正しいことを意味しない。
**引用先が腐っていないことだけ**を意味する。成果物を作り直したときに、
黙って参照が外れるのを防ぐためにある。
