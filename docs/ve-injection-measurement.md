# 過渡走行での噴射指令の追加計測

2026-10-11。VE/rf_korr の調査用。運転点の保持は要求しない。

## 今回変えたもの

従来は O₂ 電圧・STFT・λ制御状態・P回数・BA・直接読取りの rf_korr / rf_soll を記録していた。
噴射側の補正が重なった結果を確認するため、取得した診断応答から次を保存する。

| 保存列 | 意味・出所 | 取得タイミング |
|---|---|---|
| `baseInjectionMs` | `TL`、block 3 offset 6、uint16 × 0.001 ms | `standardReadTime/Ms` |
| `injection1Ms`〜`injection6Ms` | `TI1`〜`TI6`、block 19 offset 6/8/10/12/14/16、uint16 × 0.001 ms | `injectionReadTime/Ms` |
| `injectionBlankActual/Target` | `TI_AUSBLEND_IST/SOLL`、block 19 offset 4/5 | 同上 |
| `injectionStft1/2` | block 19 offset 40/42 の `LA_F_REGLER1/2` | 同上。先に読んだ RAM の STFT と別列 |
| `injectionReadSource` | `block19-0401-unverified` | 実車での新列の検証は別途必要 |

`TL` は `TI_VORST` ではない。`TI1`〜`TI6` は、slave の各補正と加算適応・気筒補正・
上下限を通過した指令時間であり、`KL_TI_UB` の無効噴射時間を加える前の値。
実噴射量や実測 AFR ではなく、噴射カット中に実際に通電したことの証明でもない。

WORKS の VE 計測は block 19 を **8サンプルに1回から毎サンプル**へ変更。
デコードと保存そのものには追加通信がないが、頻度を上げる分は約171.9 ms/sample増える。
既存通信モデルでは全体約2.74 Hz→約1.865 Hz。実車レートを保証する数字ではない。
production の block 19 は従来の1/8、通信モデル約4.563 Hzを維持する。
blockだけのfallbackも噴射時間を記録するが、O₂/BA/RAM状態が無いことはそのまま残る。

## DMEを読んで確定したこと

- master `030b84` case `0x1c` は、block 3 payload 6/7に `TL` を書く。
- master の block 19はslave担当の欄をゼロにする。これだけ読んで「TIは取れない」と判断しない。
  0401 full BINのslave `030936`〜`0309D8` は、4バイトの空欄とblanking 2バイトに続いて
  `FFE75A`〜`FFE769`の8気筒ぶんのTIを順に上位/下位バイトとして書く。
  CSLで記録するのは先頭6気筒。参照DS2カタログのoffsetと一致する。
- slave `01b0e2` は `TI_VORST` → bank別 `TI_F_ADAPT × TI_F_KATS + TI_OFFSET_ADAPT`
  → 気筒補正・同期加算・上下限 → `TI1`〜`TI6` → `KL_TI_UB` 加算 → TPU値の順。
  このためTIの記録は、STFTだけでは見えない補正の合成結果を調べる手段になる。
- `TI_F_ADAPT` と `TI_VORST` はslave専用RAMで、この0401の通常メモリ読取りでは直接取得できない。
  masterの同じ数値アドレスを代用してはならない。
- slave `027114` の `TEA1/2_F_KORR` は、学習状態と忘却状態から計算される。
  `TETV=0`だけから、その瞬間の燃料側パージ補正が1と断定できない。
  過去の履歴と全内部状態がないログから、これらを一意に再構成することもできない。

一次資料は `public/data/calibration-decomp.json` の関数、`calibration-graph.json` のRAMシンボル、
逆アセンブルノートの0401 full BIN、参照 `DmeLiveValueCatalog.cs`。
slaveの `030936` の診断応答部分は現在の関数別decomp出力に含まれないため、BIN命令列を確認した。

## 保存とTuneへの影響

追加列はリンク→`LiveMeasurement`→`LogDataPoint`→SAVE/SYNC/CSVへ渡す。
今回の変更にはD1スキーマ変更は不要で、既存の圧縮ログJSONに含まれる。
読取り失敗・短い応答・その回に読まなかった値は欠測とし、前回値や0で埋めない。
実際に読んだ0は保持する。旧ログに追加値を合成しない。

追加列は診断用で、VE採用条件・VE補正量・rf_korrテーブル・αの入力にはしていない。
現行の比較専用候補をTuneへ書き込まない制約も維持する。

## このデータで行う検証

1. 読取り成功数・実間隔・応答時間、TIの0/固定値/範囲を確認し、新列を実車で検証する。
2. block 19内のTIとSTFTを組にする。block 3のTLやRAMのBAとの比較には別々の時刻を使い、
   同じ行だから同時刻とは扱わない。応答はECU内部の原子的なスナップショットでもない。
3. 普通の走行の各通過について、rf_korr発動・BA・λ再開・STFT減少・TI変化の順序を比較する。
   TL変化やカットを区別し、STFTの減少と噴射指令の減少が対応しているかを調べる。
4. 残差があれば未記録の噴射補正を調査する。TIを追加しても、濃い側だけのO₂電圧から
   濃さの量が直接判明するわけではない。検証前にVEの修正量へ変換しない。

回転数や開度を固定して保持する走行、全開走行、追加リセットを計測成立の条件にはしない。
この追加計測は噴射経路の仮説を分けるものであり、VE定量推定が完成したという意味ではない。

## 通過中の噴射履歴を使う検証

`scripts/ve_response_history.py` と `scripts/analyze-response-history.py` に、保存後の
履歴計算を実装した。新しいフレームワークや通信項目は追加しない。

```powershell
node scripts/analyze-dme-response.mjs <取得済みセッションのディレクトリ>
npm run analyze:response-history -- <取得済みセッションのディレクトリ>
npm run verify:response-history
```

追加TIの無い旧ログは拒否し、噴射時間を合成しない。BASE/ログのSHA-256と既存の
負荷・VE座標の対応を照合する。結果は非公開の `archive/response-history/<session-id>/`
に置き、アプリのVE採用・BIN生成経路には接続しない。

### 計算の定義

- 標準・λ・噴射応答を各読取り時刻に置き、100ms格子へ補間する。これは保存後の再構成であり、
  100msごとに測定したことにはならない。範囲外や1.5秒超の読取り間隔は補間しない。
- 燃料側の入力はbank別TI平均×rpm/120、空気側の基準は2×TL×rpm/120。
  いずれも比例量であって実測質量ではない。最終TIにSTFT・BA・rf_korrを重ねて掛けない。
  TLには記録時のrf_korr/MAP等が既に含まれる。
- 実blanking=6は燃料指令の適用を0、2/4等の部分停止はbank配分不明として欠測にする。
  λ制御OFFだけでは物理履歴を消さない。停止状態の切替時刻は読取り間で不明なため、
  早期・中点・後期の感度比較を行う。
- 定数遅れ、モデル空気流量の積分に基づく移動、混合、燃料の一時貯留という13通りの
  仮説を比較する。燃料・空気の履歴を計算した後に比と対数を求める。
  貯留モデルは質量保存を満たすが、実機の壁面燃料や排気・センサーを同定したモデルではない。
- 移動した空気側の履歴にセルの寄与を残す。O₂観測時の現在セルだけへ誤差を戻さない。
  セル倍率は輸送した空気の和の内側に置き、倍率の対数を単に平均しない。

### 検証と適用範囲

外側4区間の時系列検証で、各検証区間を残した内側3区間だけから遅れ等の仮説を選ぶ。
bankを分離して学習側と検証側へ混ぜず、境界の前後20秒を学習から外す。
全仮説・両入力方式で同一の観測集合を使用する。運転点保持や同じセルへの滞在時間は条件にしない。
読取り開始／中点／終了の感度、正則化を強めた場合のセル倍率変化、P回数の複数増加も出力する。

濃薄の平均正答率とlog lossは別々に報告する。一方だけ改善しても「VE修正が正しい」とはしない。
対象セルの寄与点数は履歴に重みがあるbank観測数であり、VE修正採用数や独立な実験回数ではない。
濃い側しか無いセル、事前仮定で倍率が大きく動くセルを、点数だけで確定扱いしない。

このモデルのセル倍率は、記録時の上流空気計算を固定した条件での有効誤差である。
RFのPT1・MAP加算・VE変更に伴うrf_korrゲート変化の微分を再現しておらず、
そのまま公称VEの書換え倍率にはできない。観測した燃料入力による予測と、書換え後の
閉ループ挙動の検証も区別する。固定αや新しい固定待ち時間を導入する実装ではない。

## 修正量を決められるかの追加監査

2026-10-11。予測正答率の改善だけで完了にせず、以下を独立に確認する実装を追加した。
オフライン数値解析とPythonの検査はPython 3.12および
`python -m pip install -r scripts/requirements-analysis.txt` の環境で実行する。
ブラウザでの記録・チューニングにはPythonを使わない。

```powershell
npm run analyze:dme-air-path -- <セッションのディレクトリ>
npm run analyze:response-profile -- <セッションのディレクトリ>
npm run analyze:switch-constraints -- <セッションのディレクトリ>
npm run analyze:cut-response -- <セッションのディレクトリ>
npm run verify:dme-observability
```

- `analyze-dme-air-path.py` はBINからフィルターのraw値、RF/TL換算定数、DKBAテーブルを読む。
  `rf_soll_calc` が使う新入力の重みは `raw/16384`。カタログ表示の
  `(16384−raw)/16384` は旧値の残留率であり、秒の時定数ではない。
  細かい時間格子で座標を補間してから表を引くことと、表の出力を補間することも分けて比較する。
- `profile-response-cells.py` はセルを複数の値に固定し、隣接セルを学習区間だけで再推定する。
  全走行の指標と対象セルに寄与する観測の指標を両方出し、局所的な誤りが全体平均に隠れないようにする。
- `analyze-switch-constraints.py` は単発の濃薄切替を使う。同じセルで2周期を待たず、
  切替を挟む読取り区間の開始／中点／終了、遅れ仮説、事前仮定を変え、セル量の感度を出す。
  観測O₂電圧からAFRを作らない。この感度範囲は統計的な信頼区間ではない。
- `analyze-cut-response.py` はblankingの全停止とO₂切替の時刻をそれぞれ区間として扱う。
  先後関係が分離しない例を、確定した物理遅れとして採用しない。

#968では、全3392点のTLがBIN定数と同じ応答内のRFによる換算式に一致した。
TLを増やしても空気量の独立観測が増えたことにはならない。DKBAのSOFT/HARDは両方全0だった。
単発切替は共通2186件を利用できたが、RO10%/2200rpmへ寄与する切替は0件。
RO7.5%/2400rpmの有効空気モデル倍率は仮定により0.594〜0.800に動く。
これは適用後TLを基準にした旧比較の結果で、VEへ書き込む倍率ではない。
適用前rf_sollを基準にした再検証と、保存BASEの取り違えの訂正は下記を参照する。
詳細と図は非公開の `archive/observability-audit/<session-id>/` に保存する。

### 次に追加すべき観測と受け口

必要なのは、濃い側にあることだけでなく、その量を別に観測する手段、または濃薄の両側を挟む
既知の校正変更による比較である。同じ濃い側のログを増やすだけで修正量が決まるとは約束しない。
運転点保持は要求しない。実車の読み戻しBINと走行ログの対応も、古い保存BASEとは別に確認する。

### 記録時BINの訂正と自動保存

#965の実際のパッチ書込みを、当時のBASEと記録された設定から再構成した。
書込み履歴のSHA-256と全バイトが一致するイメージは、`k_rf_cfg=0x02`、学習停止、パージ停止だった。
#967・#968の保存BASEはそれ以前の `0x12` のままで、書込み予定のトグルも実車を表していなかった。
保存BASEだけを根拠にした `air-model-active` の全セル保留は誤りだったため撤回する。
実書込みの参照BINで再評価すると、#968の比較候補は全体5セル、対象6セルは0セルとなる。

非ゼロのMAP積分保存値は適用中であることを意味しない。#968の読取り時刻を揃えて比較可能な
93点のうち91点で、MAP値を足さない `RF=rf_soll×rf_korr` の方が一致した。
ただし診断分岐もMAPを迂回するため、この式だけで設定バイトを特定したとは扱わない。
#966には乗算学習値1/1・加算学習値0/0へのリセット後読取りも記録されている。
履歴上の書込みは現在の実車読戻しではなく、以後の未記録書込みがないことを前提とする。

`recordingCalibration.ts` はSTART時に既存の読取り専用APIでECUの2つの保存チェックサムを取得し、
同じVINの保存BINと照合する。パッチだけの書込みはSHA一致時だけ候補に含める。
練習・未来の書込み、壊れたBIN、異なるBINが同じチェックサムを持つ曖昧な照合は採用しない。
参照BINそのもの・SHA・照合時刻・チェックサム・出所をログへ同梱し、SAVE、SYNC、再読込、
クラッシュ復元を通して保持する。CSVでログを置換した場合は前の照合を引き継がない。
照合できなくてもログを記録でき、比較候補は校正不明として保留する。全バイト読戻しをしたという表示はしない。
VEが解析BASEと異なる参照にも候補を付けない。既存の従来Tuneの再生成規則は変更しない。

### 適用前rf_sollを基準にした履歴の再検証

TLは既にrf_korr適用後なので、空気モデルの基準として使うと、同じVEでもkの変動が推定倍率へ混ざる。
`analyze-nominal-response.py` は実測TIを燃料側に保ち、空気基準を
`RF_TI_CONST/1000 × rf_soll × rpm/120` とする。rf_sollの読取り時刻も別に補間する。
推定燃料の比較経路は引き続き適用後TLから作り、実測TIへkを再乗算しない。
合成検査ではkだけを1→1.2に動かしSTFTがそれを相殺した場合、公称空気基準の比が1のままになることを確認する。

```powershell
npm run analyze:dme-response -- <ログのディレクトリ> --recorded-flash <実書込みセッションのディレクトリ>
npm run analyze:recorded-calibration -- <ログのディレクトリ> <実書込みセッションのディレクトリ>
npm run analyze:nominal-response -- <ログのディレクトリ>
npm run analyze:switch-constraints -- <ログのディレクトリ> --nominal
npm run analyze:response-profile -- <ログのディレクトリ> --nominal
npm run verify:nominal-response
npm run verify:recording-calibration
```

#968の共通5226 bank観測で、時刻履歴を使う実測TIモデルのbalanced accuracyは64.56%、
log lossは0.6049。瞬時入力は57.12%・0.7386。同じ点の読取り窓の端を振ると精度は60.94〜67.57%となる。
単発切替の共通2185件でも、RO7.5%/2400rpmの倍率は時刻・輸送・事前仮定で0.696〜0.839に動く。
RO7.5%/2200・2700rpmの範囲は1を跨ぎ、RO10%/2200rpmには切替制約がない。
これはモデル感度であり信頼区間ではない。基準を直しても、対象6セルの修正量を一意にしたことにはならない。
rf_sollは独立した空気流量測定ではなく、VE変更によるRF依存ゲートの変化もこの条件付き計算では再現しない。

独立した実測λを受け取る `scripts/align-measured-lambda.py` を用意した。機器固有の接続実装や
実機検証は未完了であり、現行WORKSに外部計器が接続できるようになったという意味ではない。

入力JSONは `source`, `unit` (`lambda` または `afr`), `syncAnchors`, `samples`。
AFRの場合はその機器の `stoichiometricAfr` 設定が必要。14.7を自動補完しない。
同期点は3点以上の `{deviceTime, logTimeMin, logTimeMax}`、測定点は
`{deviceTime, bank, value, ready, valid, clipped}`。時刻は秒、bankは1か2。
機器の正常・暖機・クリップ状態が確認できない点や同期点の外側は不採用とする。

```powershell
npm run analyze:measured-lambda -- <独立λ計測のJSON>
```

時計を一定の進み率とオフセットで表せる条件下で、全同期点の範囲に収まる時計変換を求める。
一点の最小二乗合わせで時刻差を消さず、各測定の時刻の幅を残す。
同期点が矛盾すると拒否し、排気の輸送遅れと時計のずれを同一の係数へ吸収しない。
結果は `archive/measured-lambda/<入力SHA>/aligned.json` に保存し、燃焼時刻への割当てと
Tuneへの書込みは行わない。単体検査は既知の時計ずれ・ドリフト、欠測、矛盾した同期点、
AFRの基準値欠落、狭帯域電圧をλに見立てた入力の拒否を確認する。
